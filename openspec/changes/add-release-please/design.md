## Goals / Non-Goals
**Goals:**
- One workflow file, two JSON config files, zero scripts: release PR on push to `main`, tag + GitHub Release on merge, staged npm publish gated by owner 2FA (E9, E15).
- Version and changelog derived from commits; `main` always shows the last released version (E1, E3).
- Existing tag scheme `vX.Y.Z` and hand-written changelog history kept (E7, E13).

**Non-Goals:**
- Auto-publish (`npm publish` without staging) — reopen when the owner no longer wants a review step before a version goes live.
- Separate `publish` workflow on `release.published` — reopen only if GITHUB_TOKEN is chosen *and* publish must be decoupled; events from release-please's token do not trigger other workflows (E9), so the publish job lives in the same run.
- GitHub Release for the historical `v0.3.0` — reopen if the first run, after the tag backfill, still logs "Expected 1 releases, only found 0" and scans commits since the beginning of history (the same warning before the backfill is normal); then `gh release create v0.3.0` or `last-release-sha`.
- `workflow_dispatch` trigger, `draft` releases, `Release-As` overrides, pre-release channels — reopen when a release must be forced or held.
- Rewriting the 0.3.0 and earlier entries into release-please format — history is frozen (E13 keeps it).
- Adding the new job to required status checks — the release PR is checked by `ci.yml` like any PR (E8).

## Decisions
- **release-please (manifest mode) over changesets / semantic-release** — commits are already Conventional and enforced; changesets would add a second source of truth, semantic-release removes the review point the owner wants (E19, E11). Owner picks in OQ1.
- **`googleapis/release-please-action@v5`, pinned by major like the other actions** — v5 is current (node24 runtime); v4 runs on node20, which GitHub is retiring (E6, E9).
- **Config:** `release-please-config.json` = `$schema`, `bump-minor-pre-major: true`, `include-component-in-tag: false`, `changelog-sections` (`feat`→Added, `fix`→Fixed, `perf`→Changed, `docs`→Documentation), `packages: {".": {"release-type": "node"}}`; `.release-please-manifest.json` = `{".": "0.3.0"}`. No `bootstrap-sha`: the `v0.3.0` tag is found by the tag fallback (E10, E7). `include-component-in-tag` set in the config, not only the action default, so a CLI run behaves the same (E9, E10). Section names follow the existing Keep a Changelog vocabulary; `docs` shown because `LLM.md`/README changes matter to users (E2, E7). Validated with `check-jsonschema` (E12).
- **`package.json` back to `0.3.0`** — the release PR owns the bump; `main` = last published version, and `.release-please-manifest.json` agrees (E1, E14). Test E3 is unaffected.
- **Remove the `## 0.4.0 — unreleased` block, add a header note** — the updater inserts above the first version heading, so the block would leave two 0.4.0 headings (E13, E2). Its two bullets reappear as `feat(server): send usage instructions at initialize` and `docs: add LLM.md setup guide for agents` (E7) under Added / Documentation.
- **Publish job in the same workflow, `needs: release-please`, `if: needs.release-please.outputs.release_created == 'true'`** — README pattern; works for both token choices because it does not depend on a second workflow being triggered (E9). Steps: checkout, pnpm, setup-node 24 with `registry-url`, `pnpm install --frozen-lockfile`, `pnpm run build`, `npm stage publish`. Node 24 because its npm (11.19) has `npm stage`; Node 22's does not (E16). Explicit build step because `prepublishOnly` is documented for `npm publish`, not verified for `npm stage publish` (E17). `permissions: contents: read, id-token: write` on this job only (E15).
- **Release job `permissions: {}`, workflow-level `concurrency: release-please`** — the action authenticates with the PAT, so the job token needs nothing (review CUT); one run at a time so two quick pushes cannot tag or publish the same version twice. The publish job keeps `contents: read`, `id-token: write` and has no dependency cache (npm trusted-publishing guidance against cache poisoning).
- **`npm`, not `pnpm publish`, for the publish step** — npm's own OIDC + staging path is what the docs describe (E15); AGENTS.md already reserves npm for publishing (E4).
- **Token = fine-grained PAT in `RELEASE_PLEASE_TOKEN`** (owner picks in OQ2) — makes `build (22)`/`build (24)` run on the release PR so `strict` protection is satisfiable; avoids flipping "Allow GitHub Actions to create and approve pull requests" (E8, E9).
- **Docs:** AGENTS.md:56 paragraph → releases happen via the release PR, owner approves on npm, never bump `version`/edit CHANGELOG by hand; Key Files rows for the three new files; AGENTS.md:39 "npm only in the publish job"; CONTRIBUTING.md "Releases" section; CHANGELOG.md header note (E4, E5, E2).

## Risks / Trade-offs
- The release PR is authored by the owner's PAT identity → the owner cannot approve it (1 review required) → merge with `gh pr merge --rebase --admin` (admin bypass is already the owner's workflow, E8). A GitHub App token avoids this at the cost of app set-up (OQ2).
- `npm stage publish` under OIDC and automatic provenance for staged versions are documented together but not exercised here; first release confirms. Fallback: owner `npm publish` locally from the tag.
- Rebase-merge of the release PR: release-please locates the merged PR via GitHub's PR→commit association; squash is its recommended mode. If the tag does not appear after the first merge, `release-please:force-run` label or `last-release-sha` (E10).
- Fine-grained PATs expire (max 1 year) and die silently → release PRs stop appearing; the workflow log shows a 401.
- Changelog style changes from `## 0.3.0 — 2026-10-21` to `## [0.4.0](compare-url) (2026-10-22)` with commit links; accepted, header note explains.
- `docs` is not mapped to a changelog section: release-please releases whenever the generated notes are non-empty (`src/strategies/base.ts` `changelogEmpty`), so a visible `docs` section would turn every `docs(spec): fold …` commit into a patch release (review CRIT). Docs changes ride along in the next feat/fix release, unlisted.
- `release-please-action@v5` inputs may not be in actionlint 1.7.12's popular-actions database; unknown versions are skipped, not failed.

## Owner steps (outside the repo)
1. Fine-grained PAT, repository `diblaze/bokio-mcp` only, Contents and Pull requests read/write, saved as repo secret `RELEASE_PLEASE_TOKEN`; renew before it expires.
2. Right before merging the first release PR (a new trusted-publisher config expires if unused for 2 days): npmjs.com → `bokio-mcp` → Settings → Trusted publisher → GitHub Actions, owner `diblaze`, repository `bokio-mcp`, workflow `release-please.yml`, no environment.
3. After the first staged publish is approved and live: Publishing access → require 2FA and disallow tokens.
4. Each release: merge the release PR (admin bypass), then approve the staged version (`npm stage approve <id>` or the npmjs.com Staged Packages tab).

## Open Questions
1. **Release tool.** (a) *recommended* `googleapis/release-please-action@v5`, manifest config: version + changelog from the enforced Conventional Commits, release PR = review point, maintained by Google. (b) `changesets/action`: needs a `.changeset/*.md` per PR, ignores commit types, better for monorepos — duplicates what commitlint already enforces. (c) semantic-release: fully automatic on every push, no release PR, plugins for npm/GitHub, needs its own token or OIDC set-up — removes the gate the owner asked for.
2. **Token for the release job.** (a) *recommended* fine-grained PAT (repo `bokio-mcp`; Contents RW, Pull requests RW) as secret `RELEASE_PLEASE_TOKEN`: CI runs on the release PR, no repo-setting change; owner must admin-merge (author cannot self-approve) and renew the PAT yearly. (b) default `GITHUB_TOKEN`: zero secrets, but owner must enable "Allow GitHub Actions to create and approve pull requests" (E8), CI never runs on the release PR, merge is admin-bypass anyway. (c) GitHub App + `actions/create-github-app-token@v2`: PR authored by the app bot → owner can approve, CI runs, no bypass; most set-up (create app, install, two secrets).
3. **npm publish mode.** (a) *recommended* trusted publisher stage-only + `npm stage publish`: no secret, provenance, owner approves each version with 2FA (E15). (b) trusted publisher with `npm publish` allowed: live on merge, no second gate. (c) no CI publish, owner runs `npm publish` from the tag: no npm set-up, but keeps the manual step the change is meant to remove. Owner steps for (a): npmjs.com → package → Settings → Trusted publisher (GitHub, `diblaze`, `bokio-mcp`, workflow `release-please.yml`, no environment, leave `npm publish` unchecked) and Publishing access "Require two-factor authentication and disallow tokens"; per release: `npm stage approve <id>` (npm ≥ 11.15) or the web Approve button.
4. **Hand-written `## 0.4.0 — unreleased` block.** (a) *recommended* delete; the entry is regenerated from E7's commits. (b) keep the prose by pasting it as `BEGIN_COMMIT_OVERRIDE … END_COMMIT_OVERRIDE` into the merged PRs (#?) that carried those commits before the first run — owner action, same result with richer wording.
5. **Changelog sections.** (a) *recommended* `feat`→Added, `fix`→Fixed, `perf`→Changed, `docs`→Documentation. (b) release-please defaults (Features / Bug Fixes / Performance Improvements, docs hidden): one line less config, vocabulary differs from the existing entries.
